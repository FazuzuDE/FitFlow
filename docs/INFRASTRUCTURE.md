# GitHub и Oracle: подготовка инфраструктуры

## Текущее решение

Исходный код и CI размещаются в существующем репозитории
[FazuzuDE/FitFlow](https://github.com/FazuzuDE/FitFlow). На момент подключения он
публичный; изменение видимости не выполнялось.
Oracle Always Free — имеющийся у владельца сервер для будущего backend.
Мобильное приложение остаётся Expo/React Native: Oracle обслуживает API и данные,
а не исполняет мобильный интерфейс.

На этом этапе добавлен CI для мобильного приложения. Удалённый репозиторий
подтверждён владельцем, доступ к серверу и deployment пока не настроены.
Backend-кода в проекте пока нет.

Рабочее предложение для следующего этапа — PostgreSQL + API + HTTPS proxy
на Oracle. Окончательное решение между собственным API и Supabase принимается
после проверки сервера и требований авторизации. Self-hosted Supabase не следует
считать уже выбранным или установленным.

## GitHub workflow

- `main` — стабильное состояние; выпуск после успешных проверок.
- `develop` — интеграционная ветка для следующего релиза.
- `feature/<task-id>-<description>` — отдельная задача, pull request в `develop`.
- Релизный pull request: `develop` → `main`.

Workflow `.github/workflows/ci.yml` проверяет push и pull request в `main` и
`develop`. Job `Quality checks` устанавливает зависимости из lockfile, выполняет
проверки TypeScript, ESLint, форматирования, тесты, проверку конфигурации и
совместимости зависимостей Expo, затем собирает JS bundles для iOS и Android.
Экспорт JS не заменяет нативную сборку или проверку на устройстве.

После публикации репозитория включить требование pull request и обязательную
проверку `Quality checks` для защищаемых веток, если тариф аккаунта поддерживает
эти настройки для приватного репозитория. Запретить force push и удаление веток.
Для единственного разработчика не требовать одобрения другого участника.
Сам YAML не включает защиту веток — это отдельная настройка GitHub.

CI имеет только `contents: read` и не получает доступ к Oracle. Deployment
workflow появится после backend и проверки сервера; зелёный CI сейчас ничего
не публикует на сервере.

## Что нужно для подключения

1. Авторизованный GitHub CLI либо браузерная сессия для `FazuzuDE/FitFlow`.
2. SSH alias либо адрес Oracle, SSH user и путь к существующему локальному ключу.
   Ключ и пароли не нужно копировать в чат или репозиторий.
3. API-домен, если он уже есть. При отсутствии домена решение по HTTPS принимается
   после инвентаризации сервера.

## Следующий этап: Oracle staging

Сначала провести read-only инвентаризацию: ОС, CPU architecture, RAM, свободный
диск, существующие Docker workloads, занятые порты, firewall и текущие сервисы.
Не предполагать конкретную конфигурацию Always Free и не менять уже работающие
проекты без проверки.

Затем подготовить отдельный каталог/Compose project для FitFlow:

1. PostgreSQL с постоянным volume и доступом только во внутренней сети.
2. API с health/readiness endpoint, миграциями и серверной проверкой владельца
   каждой записи. Собственный API требует полноценного решения Auth — название
   «RLS-подобная авторизация» само по себе защиту не реализует.
3. HTTPS proxy, учитывающий существующую конфигурацию и подтверждённый домен.
4. Отдельную backup-копию вне диска VM и проверенное восстановление.
5. GitHub environment `staging` с минимальными полномочиями для deployment.

Deployment должен использовать конкретный успешно проверенный commit/image,
проверять SSH host key, выполнять health check и иметь возврат к предыдущему
образу. Миграции данных требуют отдельного плана совместимости. Не публиковать
PostgreSQL в интернет и не использовать `StrictHostKeyChecking=no`.

`main` → production и `develop` → staging — будущие маршруты deployment,
а не уже действующая автоматизация. Размещение двух сред на одной VM оценивается
по фактическим ресурсам; отдельные БД и секреты обязательны при таком варианте.

## Секреты

`.env.example` содержит только пример публичного URL будущего API.
Все `EXPO_PUBLIC_*` значения доступны пользователю внутри мобильной сборки.
DB credentials, signing keys и SSH private keys хранятся на сервере или в
предназначенных для них секретах CI, а не в мобильном приложении.

## Ограничения стартовой версии

Проект пока остаётся на Expo SDK 53. Проверка `npm audit` после установки
совместимых зависимостей обнаружила 18 затронутых пакетов (7 high, 11 moderate).
Предлагаемые npm исправления включают major upgrade Expo/React Native; их нужно
проводить отдельной задачей с проверкой на устройствах перед публичным релизом.
Успешный CI не означает, что audit уже чистый. Несколько затронутых пакетов могут
относиться к одной цепочке зависимостей.

`query-string@7` объявлен явно: код Expo Router 5.1.11 импортирует его, но не
объявляет в собственных dependencies. Экспорт обнаружил эту проблему после
установки текущего дерева React Navigation. Lockfile и export check фиксируют
воспроизводимый вариант до обновления SDK.
